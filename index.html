HTTP状态码

1️⃣ 信息响应（1xx）—— 临时通知

平时不太常见，但有一个是“八股新宠”：

  • 100 Continue：客户端发了大请求头，服务器回复“你继续发 body 吧”。
  • 101 Switching Protocols：服务器同意切换协议（如从 HTTP 升级到 WebSocket）。

2️⃣ 成功响应（2xx）—— 一切正常

  • 200 OK：最经典。表示请求成功。但对于 DELETE 操作，很多规范建议返回 204 更语义化。
  • 201 Created：创建成功。通常在 POST 提交数据后返回，并建议在响应头中携带 Location 字段指向新资源的 URI。
  • 204 No Content：处理成功，但没数据返回。常见于 DELETE 操作或 PUT 更新操作，告诉前端“我搞定了，但响应体是空的，你别解析”。

3️⃣ 重定向（3xx）—— 搬家了，请绕行

这是面试中的“文字游戏”重灾区：

  • 301 Moved Permanently：永久重定向。浏览器会缓存这个地址，下次直接访问新地址（SEO 会将旧权重转移给新地址）。注意：请求方法可能从 POST 变为 GET。
  • 302 Found：临时重定向（旧标准叫 302 Moved Temporarily）。每次还会访问旧地址，再由服务器指路。注意：早期规范会改变方法（POST 转 GET）。
  • 303 See Other：明确要求改用 GET。常用于 POST 提交表单后重定向到结果页（PRG 模式），防止表单重复提交。
  • 307 Temporary Redirect：临时重定向，但方法不变。如果原来是 POST，重定向时必须还是 POST（替代 302 的语义混乱）。
  • 308 Permanent Redirect：永久重定向，但方法不变（替代 301 的语义混乱）。
  • 304 Not Modified：缓存命中的身份证。客户端有缓存，服务器告诉你“内容没变，直接用你本地的”，不会返回响应体。注意：它不属于重定向，但归类在 3xx。

4️⃣ 客户端错误（4xx）—— 是你（前端/调用方）的问题

  • 400 Bad Request：语义错误或参数格式不对。比如 JSON 格式写错了、必填字段没传。千万别只返回“400”，一定要在响应体里告诉调用方具体哪个字段错了！
  • 401 Unauthorized：未认证。用户没登录，或者没提供 Token。关键：必须携带 WWW-Authenticate 头信息。
  • 403 Forbidden：已认证，但没权限。比如普通用户想访问管理员页面。很多公司会用 403 代替 404 来防止目录枚举。
  • 404 Not Found：资源不存在。可能是 URL 拼错了，也可能是数据库里查无此人。
  • 405 Method Not Allowed：HTTP 方法不对。比如只支持 POST，你却发了 GET。响应头必须带上 Allow: POST 告知客户端。
  • 409 Conflict：冲突。常见于编辑冲突（乐观锁版本号不一致），或者用户名已被占用。
  • 429 Too Many Requests：限流了。请求频率超出限制，通常响应头会带 Retry-After 告诉客户端多久后再试。

5️⃣ 服务端错误（5xx）—— 服务器扛不住了

  • 500 Internal Server Error：服务器内部未知错误。这是最通用的“万金油”报错，通常是代码抛了 NullPointerException 等未捕获异常。
  • 501 Not Implemented：功能未实现。服务器不认识这个请求方法，或该功能还在开发中。
  • 502 Bad Gateway：网关错误。通常发生在 Nginx 反向代理场景，意思是**“网关（Nginx）连不上上游服务器（如 Tomcat）”**，比如上游服务挂了或端口不通。
  • 503 Service Unavailable：服务不可用。服务器超载或正在停机维护。通常运维会配合 Nginx 主动返回此状态码。
  • 504 Gateway Timeout：网关超时。网关（Nginx）连上了上游服务器（Tomcat），但上游处理时间太久，没在规定时间内返回结果。

4.用的Agent框架是什么？ReAct模型还是Plan-and-Execute?

ReAct的精髓在于思考->行动->观察的迭代循环，类似边走边想，而Plan-and-Execute是先生成完整计划再按计划执行。、

ReAct根据每一步的观察结果动态灵活调整下一步，适用于开放式、具有探索性的任务（信息检索、科研探索）

Plan-and-Execute在开始就确定好所有步骤、执行，适用于结构化、流程化任务（如生成报告、数据处理）

5.怎么让模型不瞎编参数、准确调用工具？

一是用模型自带的function calling,它返回的就是结构化数据，直接解析

二是如果模型不支持function calling，就把工具定义写清楚，参数类型、必填项、例子给足、在Prompt里硬性要求输出json，再加一层正则解析和格式校验，不对则重试最多2次，关键参数会在后端设置默认兜底值

6.Agent的记忆怎么搞？长期短期分别怎么存？

(1)短期记忆：是当前对话或任务执行过程中的上下文状态，具有易失性。

(2)长期记忆：跨会话（Session）持久化的知识和事实，类似agent的硬盘

(3)短期记忆转长期记忆机制

大脑（LLM）：负责理解和推理，把你的模糊指令拆解成一步步可执行的计划。

记忆（Memory）：能记住上下文（短期）和你的偏好（长期），比如记住你不喝冰的。

规划（Planning）：遇到复杂任务时，能自己反思和纠错。比如订票失败，会自动尝试刷新或切换备选方案。

工具（Tools）：这是它与普通ChatBot最本质的区别。它能调用外部API、操作软件、操纵鼠标键盘，甚至控制物理机器人。

一个被封装的、可复用的函数接口（Function/API）。它接收明确的输入参数，执行一个确定的、原子性的操作，并返回明确的输出结果。

一个由大语言模型（LLM）驱动、具备环境感知能力的自主计算实体。它通过推理（Reasoning） 将模糊的、长期的目标动态拆解为实时计划，并通过循环迭代（ReAct Loop） 自主选择调用工具或子流程，直至达成目标。

一个预定义的、由有向无环图（DAG）或状态机（State Machine）描述的任务执行序列。它将一系列工具或人工操作按照固定的逻辑规则（顺序、分支、并行、循环）编排起来

我理解 Agent 和 Workflow 最核心的区别是「谁来决定下一步」。Workflow 是我提前把流程写死的，每一步怎么走都是固定的，确定性高、好控制；Agent 是让 LLM 自己决定下一步做什么，灵活但不可控。 常见的设计范式除了纯 Agent 之外，还有 ReAct、Plan-and-Execute、Reflection 这几种。 我在实际工程里用得最多的反而是把两者混用，固定流程的部分用 Workflow，需要灵活决策的节点嵌入 Agent 能力，这样既保住了整体可控，又有局部的灵活性。

215—数组中的第K个最大元素

给定整数数组 nums 和整数 k，请返回数组中第 **k** 个最大的元素。请注意，你需要找的是数组排序后的第 k 个最大的元素，而不是第 k 个不同的元素。你必须设计并实现时间复杂度为 O(n) 的算法解决此问题。

对于堆用来解决这类问题，Java 中可以直接使用 PriorityQueue 实现，其默认是最小堆。

  • 遍历数组，将元素入堆；
  • 如果堆大小超过 K，则弹出堆顶（最小值）；
  • 遍历结束后，堆顶即为第 K 大的元素。

94—二叉树的中序遍历

给定一个二叉树的根节点 root ，返回 它的 中序 遍历 。

方法一是递归：用一个方法来遍历当前到根节点的结果，故仅需递归调用根节点的左子树，然后再加入根节点，在递归调用右子树即可

时间复杂度O(n)、空间复杂度O(n)->空间复杂度取决于递归的栈深度，而栈深度在二叉树为一条链的情况下会达到 O(n) 的级别。

方法二：迭代

在迭代的时候我们显示的维护一个栈用来遍历二叉树，但是在递归的时候我们是隐式维护的。

我们用栈存储这些节点是因为在最后输出的时候是从栈顶开始输出的，这意味着最后一定是从二叉树的最底层的左子节点开始往上输出，如果当前节点有右子节点则会进栈，没有就会一直弹出栈顶也就是二叉树每一层的左子节点，但是如果有右子节点则会跑到右子树继续这个过程。

方法三：Morris中序遍历，优化空间位O(1)

根据morris序可以实现前序后序和中序遍历

Morris遍历的理解核心
没有左子树的节点只到达一次，有左子树的节点会到达两次
利用左子树最右节点的右指针状态，来标记是第几次到达

Morris遍历的过程

  1. 开始时cur来到头节点，cur为空时过程停止
  2. 如果cur没有左孩子，cur向右移动
  3. 如果cur有左孩子，找到cur左子树的最右节点mostRight
    A. 如果mostRight的右指针指向空，让其指向cur，然后cur向左移动
    B. 如果mostRight的右指针指向cur，让其指向null，然后cur向右移动

543—二叉树的直径

给你一棵二叉树的根节点，返回该树的 直径 。

二叉树的 直径 是指树中任意两个节点之间最长路径的 长度 。这条路径可能经过也可能不经过根节点 root 。

两节点之间路径的 长度 由它们之间边数表示。

分析：

对于二叉树中任意一个节点，以该节点为“拐点”的最长路径长度 = 左子树的深度 + 右子树的深度（边数）或 左子树深度 + 右子树深度 + 1（节点数）。因此，要计算整棵树的直径，只需要遍历所有节点，计算每个节点的左右子树深度之和，取最大值即可。

时间复杂度O(N),空间复杂度O(height)

  • 节点的左子树只包含 严格小于 当前节点的数。

  • 节点的右子树只包含 严格大于 当前节点的数。

  • 所有左子树和右子树自身必须也是二叉搜索树。

    递归检查左右子树

    • 左子树：所有节点值必须小于当前节点值，所以递归时更新上界为当前节点值：dfs(root.left, min, root.val)。下界保持不变（因为左子树仍要大于祖先的下界）。

    这里用Long_MIN_VALUE和Long_MAX_VALUE用来在判断的时候使另一个条件恒成立，因此仅需左子树的当前节点值作为最大值传入，而min自动由Long.MIN_VALUE替代，因此仅需要求左子树的所有子节点小于当前节点值，也就是max，其他情况为false
