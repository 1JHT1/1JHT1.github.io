4.逻辑过期方案中，value 怎么设计？请求发现逻辑过期后，为什么不能直接同步重建？异步重建时多个线程同时发现过期，怎么保证只有一个线程去重建？重建失败又怎么处理？

用set nx一条命令完成加锁 + 过期：SET lock NX PX 30000；如果两条命令分开写，如果客户端宕机，锁就永远不过期，形成死锁。

释放锁不是简单 DEL，而是“判断是不是自己的锁 + 删除”两步。如果分开做，会有经典并发 bug
example:
线程A: GET lock → 发现是自己的锁
（此时锁恰好过期）
线程B: SET lock NX PX 30000 → 拿到锁
线程A: DEL lock → 把B的锁删了！

必须把“比较 value + 删除”做成原子操作，Lua 脚本在 Redis 中单线程原子执行，执行期间不会被其他命令插入：

线程A 拿到锁，过期时间 30s
线程A 业务执行了 40s
→ 30s 时锁自动过期
→ 线程B 拿到锁开始执行
→ 此时 A 和 B 同时持有“锁”，并发冲突
→ 40s 时 A 执行释放锁 Lua，发现 value 不是自己的，删除失败（还好没删错）

WatchDog自动续期机制：
Redisson 的经典方案----【加锁成功后启动后台定时任务，每隔过期时间/3 检查一次，如果业务还没执行完就重置过期时间。只要客户端存活，锁就不会因业务超时被释放。客户端宕机后定时任务停止，锁自然过期，不会死锁。】

每次加锁返回单调递增的版本号，下游资源写入时校验版本号，拒绝旧持有者的过期写入。即使锁失效，也能防止旧线程覆盖新线程结果。

AI Agent 是以 LLM 为“大脑”，具备感知、记忆(memory)、规划(plan)、工具调用(tool)、反思能力，能在环境中自主循环执行以完成目标的智能体系统。

架构层面：
简单 LLM 调用是“输入 → 输出”的单次映射；Agent 是“目标 → 规划 → 行动 → 观察 → 再规划”的闭环控制循环，LLM 从“生成器”变成了“决策器”。

执行模式区别：
LLM 在循环中做决策”，而不是“LLM 一次性生成答案

ReAct 模式中，LLM 是如何决定“下一步该调用哪个工具、传什么参数”的？

LLM通过function calling机制决定调用工具和传递参数
（1）工具定义以 JSON Schema 的形式随请求下发给模型
（2）模型在 Thought 中推理，在 Action 中输出结构化调用请求
（3）应用层做校验，执行后把结果回传

工具调用的结果（Observation）又是如何反馈给 LLM 的？
ReAct 的每一轮循环都会把 (Thought, Action, Observation) 三元组追加到对话历史中。工程实现上，工具执行结果通常被包装成一条结构化的工具消息，格式如 Observation: { … }，再拼接到下一轮 prompt 中

如果工具返回了错误或无关信息，Agent 通常怎么处理？
错误不是被“吞掉”，而是被转化为新的 Observation，让模型基于新证据自我修正。
